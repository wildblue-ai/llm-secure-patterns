# Architectural Decision Items — Run 3 Adversarial Review

Design questions requiring a decision before code changes. Each item has two or more options; the suggested resolution is a recommendation, not final. Review and mark each as **Accepted / Modified / Deferred** before starting implementation.

Source: Run 3 findings (2026-04-14). Fix-now items that are straightforward code or doc fixes are tracked in findings-plan.md. Only items requiring a design decision are listed here.

---

| # | Name | Description | Suggested Resolution |
|---|------|-------------|---------------------|
| 1 | Separate inference pool — Claude API viability | Level C in secure-external-ingestion recommends "separate inference pools" but no such isolation primitive exists in the Claude API. Developers may act on guidance that isn't implementable. | Reframe as conceptual guidance with a caveat: "No API-level isolation exists today — mitigate by using separate API keys with distinct system prompts and rate limits per trust tier." |
| 2 | Token estimation heuristic — ship or require real tokenizer | `len(text)/4` is presented as working Level A code despite systematic underestimation for CJK/emoji. Risk: developers copy-paste it into production. | Ship the heuristic with a prominent `# WARNING: NOT PRODUCTION-SAFE` block comment AND add a separate code block showing tiktoken usage. Give developers both paths explicitly. |
| 3 | Input size check — elevate or remove | The `len(request.message) > MAX_INPUT_CHARS` check in endpoint-hardening Level A has a parenthetical warning about CJK/emoji. A parenthetical is easy to miss and ignore. | Promote the warning to a `# WARNING` inline comment directly above the check, matching the style already used in Level B. No behavior change needed — just visibility. |
| 4 | Output-validation trigger scope vs. HTML-only implementation | SKILL.md trigger says the skill applies when output is used in "SQL, shell commands, or code that gets executed" — but templates only cover HTML text-node escaping. SQL and shell have different escaping needs entirely. | Narrow the trigger description to HTML/markup rendering contexts only. Add a note: "For SQL, use parameterized queries; for shell, use subprocess with argument arrays — not string escaping." Do not add SQL/shell templates to this skill. |
| 5 | `sanitize_html_output` function name implies context-agnostic safety | The function uses `html.escape()` which is only safe for HTML text nodes. The name misleads developers into using it in attribute, script, or URL contexts where it is unsafe. | Rename to `escape_html_text_node()` in the template and update all call sites and SKILL.md references. Add a docstring note: "Safe for text-node insertion only. Not safe for attribute, JS, CSS, or URL contexts." |
| 6 | Fail-closed logic uses string-matching on warning messages | The output-validation fail-closed block checks for substrings like `"Possible SSN"` in warning strings. If any scan function's message wording changes, the fail-closed behavior silently breaks with no indication. | Refactor scan functions to return structured dicts (`{"type": "pii_ssn", "severity": "critical", "match": "..."}`) and match on `type` field. This is a breaking change to the template API — worth doing before v1.0.0 release. |
| 7 | Dual-prompt architecture — no implementation path given | System-prompt-design Level C recommends "dual-prompt architecture" as a primary control but provides no API-call-level guidance. Claude's system prompt is not confidential from the model regardless of how it's passed. | Reframe with a caveat: "No API placement makes a system prompt inaccessible to the model. Dual-prompt refers to separating *user-visible* instructions from *internal reasoning* — not achieving cryptographic confidentiality." Provide a concrete example using the `system` parameter vs. assistant prefill. |
| 8 | Output filter for Level C — no template or adversarial guidance | System-prompt-design Level C recommends a `+1 LLM call output filter` but provides no filter prompt template and no discussion of the filter's own susceptibility to adversarial evasion. | Demote to v1.0.1 with a cross-reference: "A filter prompt template with adversarial evasion caveats will be added in v1.0.1. For now, implement a keyword blocklist for known system prompt fragments as a starting point." |
| 9 | Credential regex patterns — illustrative vs. maintained | Patterns like `sk-[A-Za-z0-9]{20,}` miss current formats (`sk-ant-api03-*`, `sk-proj-*`) and formats change without notice. Shipping them as working code creates false confidence. | Add a prominent caveat to the template: "These patterns are illustrative only and will become stale. For production use, integrate truffleHog or detect-secrets which maintain up-to-date pattern sets." Do not attempt to maintain patterns in this repo. |
| 10 | Cross-tag escape — only escapes current iteration's tag | `build_system_prompt` escapes the current tag name in each content block but not other registered tags. An attacker can close one UNTRUSTED block and open a different one using another tag name in the same content. | Escape ALL registered tag names (not just the current one) in every content block. This requires collecting all tag names first, then applying a single combined regex. This is a code fix but requires a design decision on whether to use a combined regex or per-tag loop. |
| 11 | `CLEAN` output label creates false confidence | The demo code in `system_prompt_template.py` and `output_schema_validator.py` prints `"Credential scan: CLEAN"` — a binary pass signal that contradicts the caveats in the docstrings. CI pipelines may parse this as a green gate. | Change all demo output to `"No patterns detected (not a guarantee of absence)"`. This is a low-effort change with high impact on the tool's credibility. |
| 12 | Destructive tool denylist — expand or flip to allowlist | `DESTRUCTIVE_TOOL_PREFIXES` misses `post`, `put`, `patch`, `execute`, `run`, `invoke`, and many others. The caveat is buried in a docstring. The denylist model is fundamentally incomplete — there is always another prefix. | Flip to an allowlist model: define `SAFE_READ_PREFIXES = {"get", "list", "read", "fetch", "search", "describe"}` and flag anything not on the list. This is stricter but more defensible. Add a `# WARNING` block at the call site, not just in the docstring. |
| 13 | Stage 1 write-permission enforcement language | SKILL.md says "Stage 1 NEVER has write permissions" (imperative) but `validate_pipeline()` only emits a warning and cannot enforce this. The gap between the language and the implementation misleads developers about the actual protection in place. | Change SKILL.md language to: "Stage 1 should not have write permissions. `validate_pipeline()` will warn if it detects them but cannot enforce this at runtime — enforcement is the operator's responsibility." Also add a `validate_or_raise()` variant that blocks on violation. |
| 14 | MCP tool schema injection — in scope or out | The skill addresses MCP tool *results* but ignores that tool *names*, *descriptions*, and *parameter schemas* are also attacker-controlled if the MCP server is untrusted. These influence model behavior before any tool result is processed. | Add a Level B caveat in SKILL.md: "MCP tool schemas (names, descriptions, parameters) are attacker-controlled if the MCP server is compromised. Validate schema structure at registration time and treat tool descriptions as untrusted input." Reference Palo Alto Unit 42 MCP research. |
| 15 | Audit logging "full context" creates LLM02 surface | Level C recommends audit logging "with full context" in agent-action-surface without any guidance on PII scrubbing, access controls, or retention limits. Full-context logs can expose credentials, PII, and system prompt contents. | Change "full context" to "relevant context" and add: "Do not log raw system prompts, credentials, or unredacted PII. Scrub sensitive fields before writing to logs. Apply access controls and retention limits appropriate for the sensitivity level." |
| 16 | `trusts_input_from=None` default silently suppresses warnings | In isolated_pipeline.py, `trusts_input_from: str | None = None` defaults to treating a stage as having no declared trust source, which can suppress write-access warnings for stages that simply forgot to declare it. | Make `trusts_input_from` a required field with no default, so omitting it is a validation error at pipeline construction time, not a silent pass. |

## How to use this document

1. Review each item and mark the **Suggested Resolution** column as: **Accept** / **Modify: [your change]** / **Defer to v1.0.1**
2. Items marked Accept or Modify move to the fix backlog and get tracked in findings-plan.md
3. Items marked Defer get added to the v1.0.1 section of findings-plan.md
4. After decisions are recorded, implementation can begin without further design debate

**Priority note:** Items 5, 6, 10, 11, 12, 13 are high-confidence quick wins — the suggested resolution is clear and the implementation is straightforward. Items 1, 7, 8 require the most judgment.
